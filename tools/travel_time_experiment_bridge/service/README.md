# שירות הכנה מקומי

מימוש Python stdlib בלבד, הנשען על `../implementation`. השרת מאזין **רק** ל־`127.0.0.1`. אין פנייה לקלוד, לאופטיבוס או לשום שירות חיצוני. Worker יחידת עבודה יוצר חבילת מסירה פרטית ועוצר ב־`blocked_adapter`. אין סטטוס הצלחת פעולה באופטיבוס.

## הפעלה

יש להכין תיקייה פרטית, קובץ טוקן וקובץ registry בבעלות המשתמש. הרשאות התיקייה 0700 והקבצים 0600. מומלץ לייצר טוקן אקראי של 32 בתים באמצעות `secrets.token_urlsafe(32)` ולשמור ישירות לקובץ; בחיבור כלים אין צורך להדביק טוקן בדפדפן או בפרמטרי פקודה; דף ההדגמה מאפשר הזנה ידנית בזיכרון בלבד. קובץ registry נבחר בידי מפעיל השרת, והוא מכיל בדיוק:

```json
{"schema_version": 1, "snapshots": ["כאן אובייקטי snapshot לפי חוזה implementation; לא מחרוזת"]}
```

המבנה למעלה הוא המחשת המעטפת בלבד. כל snapshot חייב לעמוד בחוזה המקור המלא, כולל ראיות. מותרת רק רשומה עדכנית אחת לכל צמד `dataset_id` ו־`schedule_id`. החלפת registry נעשית אטומית בידי המפעיל; אין endpoint לטעינת snapshot מהלקוח. owner-only והטוקן הם הגנה מקומית, ואינם הוכחה לאמיתות מקור או להרשאת שינוי באופטיבוס.

מהתיקייה הזאת, עם נתיבים מוחלטים לקבצים שבבעלותכם:

```sh
python3 local_bridge.py serve --state-dir /private/path/state --registry /private/path/registry.json --token-file /private/path/token
python3 local_bridge.py submit --payload /private/path/payload.json --token-file /private/path/token
python3 local_bridge.py worker-once --state-dir /private/path/state --registry /private/path/registry.json --token-file /private/path/token
python3 local_bridge.py status --job-id JOB_ID_FROM_SUBMISSION --token-file /private/path/token
```

פורט ברירת מחדל 8765; `--port` חייב להיות זהה בשרת ובלקוח. `--implementation` מאפשר למפעיל לבחור את תיקיית ליבת החוזה; זה נתיב קוד מקומי מהימן, לא שדה לקוח. הלקוח קורא את הטוקן מקובץ ומוסיף Bearer בעצמו. דפדפן מייצא חבילת JSON, והגשה מתבצעת באמצעות CLI. אין צורך ב־CORS ואין החזרת כותרות CORS. ברירת המחדל דוחה כל בקשה שיש בה Origin. רק אם נדרש, `--allowed-origin http://localhost:PORT` מאפשר Origin מדויק; אין wildcard, ואין endpoint לפקודות, פרומפטים או קבצים.

## גבולות ובדיקות

- `POST /jobs`: גוף JSON עד 2 MiB, תוכן `application/json`, ללא מפתחות כפולים או NaN/Infinity. נדרש Bearer בהשוואת זמן קבוע ו־Host מדויק `127.0.0.1:PORT`. כותרות Host/Origin/Authorization כפולות נדחות. Transfer-Encoding נדחה.
- `GET /jobs/{opaque_id}`: מזהה, מצב וספירות בלבד. אין נתוני נסיעות, מקור, טוקן או קבצי מסירה בתגובה.
- בהגשה נבחר המקור מה־registry ומבוצע חוזה מלא. בזמן claim המקור נטען ונבדק שוב, כולל digest של מלוא הראיות. שינוי מקור או ראיה בין שלבים מסתיים ב־`failed` לפני יצירת חבילה.
- Worker שומר `artifacts/{job_id}/handoff.json`, הוראות בעברית ו־manifest. כל הנסיעות נשמרות בחבילה, גם אלו שלא משתנות. נתיבי הפלט נוצרים בשרת ממזהה אטום; הקבצים פרטיים ונכתבים באמצעות החלפה אטומית ו־fsync. אין retry אוטומטי.
- במקרה קריסה, הליבה תומכת ב־reconciliation, אך CLI זה אינו מבצע recovery אוטומטי. יש לעצור workers ולבדוק את המצב לפני שימוש ידני ב־API הליבה. חבילה חלקית או חבילה במצב failed אינה אישור לפעולה.
- השרת מיועד לניסוי מקומי, לא לחשיפה לרשת או לשרת production. משתמשים או תהליכים עם אותה זהות מערכת יכולים לשנות קבצי מקור; הרשאות קובץ אינן מגינות מפניהם. אין אימות רשמי של אופטיבוס.

```sh
python3 -m unittest discover -s tests -v
```

הבדיקות משתמשות במקור סינתטי בלבד: הגשה ו־CLI, הכנת חבילה מלאה, GET מוגבל, מקור/ראיות שהתיישנו, כפילויות, הקשר Origin/Host, אימות Bearer, גודל גוף, תוכן לא תקין והרשאות קבצים. אין בבדיקות הוכחת כשירות למידע אמיתי או ניסיון באופטיבוס.

## דף הדגמה בעברית

`GET /` מגיש דף סטטי ללא סודות וללא אימות; `GET /demo.js` מגיש את הקוד הקבוע שלו. Host עדיין נבדק. דף זה אינו מציג נתונים עד שהמשתמש טוען קובץ בעצמו, ואינו ניגש ל־registry. כדי לאפשר שליחה מאותו דף, הפעילו את השרת עם `--port 8765 --allowed-origin http://127.0.0.1:8765` ופתחו את הכתובת המוצגת. רק ה־Origin המקומי המדויק הזה מותר; אתר ציבורי אינו מותר. אין localStorage, cookies, יומני בקשות או טוקן משובץ בדף. `POST /jobs` ו־GET סטטוס עדיין דורשים Bearer.

הממשק מציג מקור, סניף, תאריכים ומספר שינויים לפי הקובץ שנטען, כתצוגה מקדימה בלבד; האימות הסמכותי מתבצע בשרת. אין כרגע registry אמיתי מאומת שמאפשר לקדם את מועמדי המנוע לשינוי.

במצב `failed`, הסטטוס כולל קוד מוגבל: `stale_registry` למקור/ראיות שאינם ניתנים לאימות מחדש, או `preparation_failed` לשגיאת הכנה. נשמר קובץ כשל פרטי עם הקוד בלבד, ללא חריגה גולמית. אם מערכת הקבצים אינה מאפשרת לשמור קוד, מוחזר הקוד הכללי.

## קריסה והסגר של נתונים פגומים

`claim_next` בודק את החבילה השמורה לפני מסירתה ל־worker. JSON פגום, הפרת חוזה או אי־התאמה ב־digest/run_id מעבירים את הפריט למצב הסופי `failed_integrity` ורושמים audit באותה עסקה. הנתונים המקוריים נשמרים לחקירה; אין ניסיון חוזר ואין מעבר יציאה מההסגר. התור ממשיך לפריט התקין הבא. כשכל הפריטים בהסגר, worker מחזיר `null` — אין בכך ביטול של ההסגר שנשמר.

`GET /jobs/{id}` עבור פריט בהסגר מחזיר `counts: null` ו־`failure_code: stored_integrity_failed` בלי לפענח את ה־JSON הפגום ובלי לחשוף אותו. הממשק מציג שהספירות אינן זמינות.

קריסה אחרי claim היא מצב נפרד: רק לאחר עצירת כל ה־workers אפשר להפעיל ידנית את `recover_inflight()` בליבה, שמסמן claimed/prepared כ־`reconciliation_required`. הוא אינו מנסה שוב ואינו משחרר פריטים מהסגר. CLI השירות אינו מפעיל recovery אוטומטי.

### חיזוק זמינות השירות

השרת מגביל ל־16 בקשות פעילות במקביל; חיבור עודף נסגר מיד. timeout של חמש שניות נקבע עם קבלת החיבור, ולכותרות יש גם deadline מוחלט של חמש שניות כדי שטפטוף בתים לא ישאיר חיבור פתוח. בדיקת הרשאות מסד הנתונים משתמשת ב־descriptor ו־fstat בלבד ואינה קוראת את תוכנו.

אם נתון בתור נפגם לפני claim, GET סטטוס מחזיר את המצב השמור עם `counts: null` ו־`stored_integrity_failed`, בלי לשנות את התור או לחשוף את הנתון. ההסגר עצמו מתבצע ב־claim.
